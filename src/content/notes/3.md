> 在开发具身 Agent Harness 的过程中，我在项目本体功能之外逐渐形成了不少辅助自己和 Coding Agent 长期维护 Vibe Coding 项目的工作，感觉可以分享给大家参考。不过我暂时不想自己额外花精力去慢慢复盘，因此先偷了懒让 AI 帮我从项目中提炼经验，我只按自己的风格稍作修改。后续有余力再整理为一篇正式的博客叭。

---

Vibe Coding 是一种开发形态：需求以自然语言下达，Agent 负责搜索、实现、验证与文档同步，项目在多次会话、多个 Agent、多个阶段中持续生长。本文只讨论功能代码之外的元工作，不涉及具体业务实现与技术选型。这种形态把“写出代码”的成本压得很低，却把“让下一次会话理解这个项目”的成本推得很高。失效通常有三类：

1. **会话失忆**：不知道上次为什么这样改，于是重新设计、重复返工。
2. **边界猜错**：分不清哪些是硬约束、哪些只是当前实现，于是按自己的理解改坏。
3. **完成不可验证**：任务被标记 Done，却没有可复跑的读数，下一次才发现是假完成。

解决上述问题的一个方案是**把代码库做成一个会自我解释的系统**——入口说明怎么工作，任务说明做什么，规则说明不能做什么，验证说明是否真的做成，历史说明为什么。

# 1 核心模型

长期项目里的知识寿命不同，如果塞进了同一个文件或目录，结果通常有两种：长期文档被短期内容污染，短期内容过期后难以取舍。

| 知识类型  | 回答的问题     | 典型载体            | 寿命     | 维护时机    |
| ----- | --------- | --------------- | ------ | ------- |
| 意图与边界 | 为什么做、不做什么 | 评估登记、流程纪律、边界登记  | 长期     | 决策时签认   |
| 方向与计划 | 下一步做什么    | 计划草案、共享设计文档     | 中期     | 审计或设计演进 |
| 工作与历史 | 做过什么、怎么验收 | 任务跟踪、开发日志、过程缓存  | 任务或阶段  | 任务收口时   |
| 事实与接口 | 系统怎么工作    | README、文档站、模块参考 | 与代码同寿命 | 改代码同轮   |
| 机器状态  | 当前进度与拓扑   | 进度数据、架构数据、生成页   | 快照     | 生成时     |

由此得到三条原则：

- **寿命分离**：长期规则不写进任务，过程日志不写进文档站，生成产物不入库。
- **单一真相**：同一事实只在一处维护读数，其他地方只做指针或镜像。
- **可重跑**：结论必须能由命令、脚本或构建重新验证，而不是只存在于聊天记录里。

我的项目管理框架总览：

- **docusaurus 文档站**：架构文档 + （评估登记 + 开发纪律 + 边界备案）

- **backlog.md 任务管理器**：计划草案 + 任务跟踪 + 开发日志

# 2 入口分工

Agent 不会从代码里自动推断“这个项目用任务跟踪工具管工作、用计划草案管未来、用过程缓存记录证据、用文档站管长期知识”，这些必须写进入口文件。

| 载体 | 面向 | 作用 |
| - | - | - |
| `AGENTS.md`（或同类说明） | Agent | 可执行的工作契约：结构、命令、硬约束、已知坑、任务与文档流程 |
| `README.md` | 人 | 系统全景、模块总表、验证入口 |
| 开发者文档站 | 开发者 | 概念、指南、参考、维护；可构建、可断链校验 |
| 任务跟踪工具 | 人与 Agent | 任务、计划草案、里程碑、开发日志、共享设计 |
| 过程缓存目录（如 `devlogs/`） | 执行 Agent | 过程日志与证据；不入库、不入站 |

入口文件只写第一屏必须知道的东西：

- 项目分几层、核心边界在哪、哪些依赖与目录是禁区；
- 最常用的命令与最小回归集；
- 组件与接口、参数、生命周期、后台服务的关键语义；
- 已知坑与硬约束：线程亲和、共享资源、固定频率、严格校验、版本一致性；
- 交付、验收、基线日志写在哪里，任务与计划登记在哪里，以及对应的创建、执行、收口与标签规则。

每次会话的固定步骤：

1. 读 Agent 说明文件，需要时读 `README.md`；
2. 读任务跟踪工具的工作流说明，再按需读创建、执行、收口指南；
3. 先搜索已有任务、计划草案与历史记录，确认没有重复工作；
4. 看 `git status`，确认哪些是用户未提交的改动，不替用户提交；
5. 需要设计决策时先给方案与计划，得到批准再动手。

# 3 任务账

*任务账和方向账两节均基于 Backlog.md 展开。*

任务不是待办清单，而是一份**可检索的承诺**：为什么做、做完是什么样、怎么验证、最后实际做了什么。任务结构包含六项：标题（一个可独立交付的专项）、描述（问题、范围与关键提交）、验收标准（AC，可逐条勾选）、实现计划与笔记（执行期的方案与读数）、最终摘要（改了什么、怎么验证）、标签与引用。前五项决定任务是否可读，最后一项决定任务是否可检索。

## 3.1 任务粒度

一个任务对应一个可交付专项，而不是一次提交。历史回填时，同一专项的开发、返工与验收聚合在一条任务里，零散修复才放进“其他变更”；任务内部可以保留多个提交与返工轮次，对外只有一个承诺。这个粒度既让任务可读，也让开发日志不必逐提交罗列。

## 3.2 独立验收

把实现与验收分开：实现者写入自检读数，独立验收者按 AC 逐条复核，不通过就把任务退回进行中、取消已勾选的 AC，并把结论写进开发日志。关键不在验收者更聪明，而在验收者没有实现者的沉没成本——实现者可以乐观，验收者必须悲观。历史通过不能替代当前验收，失败记录也不该被“面板变绿”覆盖。

## 3.3 里程碑

里程碑按阶段聚合任务，完成度由任务状态推导，不手工维护；它只回答一个问题：这个阶段到底结束了没有。任务没关，里程碑就不该显示完成。

## 3.4 标签

任务通常已有 `type`、`priority` 与 `milestone`，标签不应重复这三者，而应补充领域、性质、来源与所有权四个维度。领域包括核心、接口、Agent、数据、状态、文档等，一个任务允许 2–4 个；性质包括架构、重构、稳定性、性能与协议，没有跨领域性质就不加；来源标记历史回填或外部导入；所有权只用于所有者本人创建的草案。标签不是越细越好，与前三者重复只会让筛选维度混乱。

# 4 方向账

未来计划可能被两种东西腐蚀：静态路线图页离执行太远，半年后没人知道哪条还算数；过期任务占着看板，却没人敢关。更耐用的做法是把未来计划登记为**计划草案**，与任务放在同一个跟踪工具里，让它天然可筛选、可过期。

- 按模块、功能或机制提炼，一条草案只回答“下一步可能做什么、为什么现在做”；
- 可以有优先级、标签与引用，但不要求完整设计，跨草案共享的长期设计放独立文档；
- Agent 可以根据会话创建草案，开始相关工作时按最新计划创建任务；
- 草案不直接转成任务，完成后的草案由所有者手动归档或删除。

计划草案比静态路线图耐用，原因有四：它与任务在同一工具里，优先级、标签、引用与状态都能筛选；它允许方向保持模糊，不必为了填页面而假装精确；它天然可过期，所有者可以归档、重写或合并；它把“谁创建的”变成可见信息，避免 Agent 误删用户的方向。

一个常见链路是：全面审计产出若干草案，其中一条被派发为任务，任务独立验收未通过，草案仍然保留。草案不是任务的附件，而是所有者判断“这条方向还要不要继续”的锚点。

# 5 规则账

长期规则需要少而稳。一个最小组合是三份长期登记：

| 文档 | 负责 | 不负责 |
| - | - | - |
| 评估登记 | 先评估后排期的重大变更：收益、代价、风险、行动、状态 | 具体实施、任务拆分 |
| 流程纪律 | 文档同步、验证脚本维护、过程日志、dogfooding、边界签认、构建与提交 | 产品计划、一次性验收 |
| 边界登记 | 所有者拍板或追认的“不做什么” | 待办、尚未签认的候选 |

几个具体做法：

- **边界由所有者签认**：Agent 可以提出候选边界，但不能把“建议不做”写成“项目不做”。
- **重大变更先评估再排期**：评估项要有背景、收益、代价、风险、行动与状态，结论未明确前不排期。
- **dogfooding**：机制宣布建成前至少要有 1–2 个真实使用方使用并登记证据，否则容易出现机制建好、所有组件都绕开它的假建成。
- **纪律要可执行**：不是“要写文档”，而是“改什么同步哪一页”“脚本怎么准入、分层、淘汰”“日志写哪里、何时清理”。

这些边界需要：不依赖 Agent 记住，而依赖测试、grep、注册期校验、文档页与代码结构去强制。能写成检查的，不要只写成提醒；只能写成提醒的，放进入口文件的“已知坑”，并在每次踩坑后回填。

# 6 过程账

Coding Agent 工作会不断产出验收、交付、返工等过程文档，可以按过程缓存和开发日志分层维护，避免盲目堆积。

## 6.1 过程缓存

- Git 忽略，不入库、不入站；
- 存放交付、验收、返工与基线日志及配套证据；
- 按专项与阶段命名，一篇一阶段；
- 阶段收口后清理，删除前确认结论已沉淀进长期文档、计划草案、开发日志或事实页；
- 站内引用一律用行内代码路径，不用 Markdown 链接，避免断链。

## 6.2 开发日志

- 一条任务一条记录，阶段、返工与验收合并，不进文档站；
- 只从提交历史提炼，不复制提交正文，不贴证据；
- 条目按时间倒序，后续返工并入原条目；
- 维护带**记录游标**，只推进到最后一条任务提交，纯文档、纯日志、验收记录提交不计入、不推进：

```
git log --reverse --date=short --pretty='%h %ad %s' <游标>..HEAD
```

游标规则看似琐碎，实际是长期维护的关键：它让“上次记到哪”不再依赖人的记忆，也让大量文档与验收提交不会把游标推到没有意义的位置。典型情况是独立验收记录写进了开发日志，但不推进游标，因为真正的任务提交尚未收口。

过程缓存是过程，可以很长、可以带证据、可以过期、可以删除；开发日志是历史，短、稳定、可读、不删；长期文档是结论，只留规则、边界与评估，不贴过程。三者混写，过程就会以“完整”的名义长期滞留。

# 7 文档工程

静态文档站的价值不只是版面，而是文档可以被 CI 式地验证：目录即侧边栏，新增页面不用手工维护；`onBrokenLinks` 设为失败，断链即构建失败；过程内容不进站。文档分四层：

- 概念：系统为什么这样设计、关键术语与执行语义；
- 指南：新增模块、组件、后端与服务的端到端走查；
- 参考：API、参数、错误与生命周期；
- 开发与维护：长期登记、回归验证、评测、术语表与调试入口。

同步责任要落成一张“改什么，同步哪页”的表：接口契约、配置 schema、执行语义、宿主行为、后端接口、模块注册表、验证脚本、任务收口。原则只有一条：**改公共契约的提交，必须包含对应文档页的 diff。**

内容规范可以压缩成三条：统一语言与术语，发现混称先统一术语再改内容；代码摘录从源码实摘，不写假想 API，无法保持同步的示例宁可不写；面向使用者的页面不使用内部阶段与缺陷编号，编号只留在专项页、开发日志与缓存区。含硬约束的页面在页首列“硬约束速查”，页尾列“本页涉及脚本”，全站权威脚本总表固定在回归验证页。

# 8 验证入口

长期项目不一定需要重型测试框架，但需要可复现的验证入口：每个改动都能对应一个或一组命令，命令失败退出码非 0，文档构建与数据校验也纳入验证，验证结果写进任务与日志，而不是只存在于终端滚动里。

验证脚本不是越多越好。脚本数量增长后，常见问题是同一验收面多份实现、夹具整段复制、过程性基线脚本滞留。一次收敛通常包括三步：删除使命已结束的基线脚本，因为冻结快照会随代码演进失真；把同验收面的阶段脚本合并到终态脚本，并提取共享夹具作为单一来源；把准入、角色、生命周期、去重、镜像同步与收口评审写进流程纪律，其余收敛项登记为计划草案，按触发条件处理。

关键规则是**角色分层**：回归集、全量自检、标定观察工具。不是每个脚本都承担回归义务，标定观察工具的对照、扫描与直观观察能力就是保留理由，不能因为不在回归集里，在收口时被误删。

验收的判据只有证据：AC 逐条勾选，勾选必须有对应的读数；负例（反例、边界、失败注入）保留为永久回归，不要只留正向通过；已知存量失败单列，不能混进全绿。独立验收的价值不在让面板变绿，而在让未关闭的风险保持可见。

# 9 清理节奏

长期维护还需要持续对抗熵增，对过时和冗余文件进行清理。清理按三个节奏进行：

| 时机      | 做什么                                                   |
| ------- | ----------------------------------------------------- |
| 每个任务收口  | 更新 AC 与最终摘要；更新开发日志；推进游标；同步文档；清理对应过程缓存                 |
| 每个阶段收口  | 清点验证脚本；清理过阶段过程日志；检查草案是否有效；更新里程碑                       |
| 每季度或大审计 | 文档站去编号化、术语统一、断链检查；三份登记复核；归档完整性；生成器 `--check`；命令与脚本表镜像 |

清理的边界同样重要。以下五类不删：所有者创建的草案、活跃阶段的过程日志、长期登记文档、归档目录（除非有新的归档或迁移结论）、开发日志的历史条目。被推翻的结论就地补注，不重写历史。

# 10 最小落地

如果只做五件事：写一个可执行的 Agent 说明；建一个任务账，包含 AC、最终摘要与状态；建三份长期登记，边界由所有者签认；建过程缓存与任务级开发日志，后者带游标；建可复跑的验证，包括最小回归集、脚本与文档构建。

第一周只需要骨架：Agent 说明、README、文档站骨架、任务跟踪初始化、一份过程缓存章程、一个最小验证命令，以及覆盖过程缓存、生成产物与密钥的 `.gitignore`。第一个月把生命周期跑通：搜索、创建、执行、独立验收、返工；三份登记建立并完成第一批边界签认；计划草案、开发日志与游标投入使用；验证脚本完成角色分层并至少清点一次。

# 结语

元工作的收益不在仓库更整齐，而在降低三项成本：重新解释、重复返工、假完成。让下一次会话的维护者知道上一次为什么这么做，让下一个 Agent 不需要猜，让每一条“完成”都能被重跑。
